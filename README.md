# فریا · FARYA Chef Console

سامانهٔ محاسبهٔ **بهای تمام‌شده** و **قیمت‌گذاری منو** برای سرآشپزِ رستوران فریا.
رابطِ فارسی (RTL)، تقویمِ شمسی، و محاسبهٔ زنده از مادهٔ خام تا حاشیهٔ سود.

## وب‌سایت عمومیِ رستوران

- صفحهٔ اصلیِ مشتریان: `https://farya-pitza.ir/`
- دفترِ امنِ بهای تمام‌شده: `https://farya-pitza.ir/cost` (نیازمند ورودِ سرآشپز)
- منوی آنلاین مشتریان: `https://farya-pitza.ir/menu`؛ همان دادهٔ هفت پیتزای صفحهٔ اصلی را استفاده می‌کند.
- پروژه یک Vite SPA است؛ `vercel.json` مسیرهای عمومی، `/menu` و `/cost` را به
  `index.html` بازنویسی می‌کند و خودِ برنامه هر مسیر را جداگانه نمایش می‌دهد.
- قیمت آنلاین فقط از RPC خواندنیِ `farya_public_menu()` و برای کدهای allowlist‌شدهٔ
  `FARYA-*` دریافت می‌شود؛ هیچ بهای مواد، مقدار رسپی یا سرباری در دسترسِ کاربر عمومی نیست.
  تا وقتی هفت آیتم با این کدها و قیمت فروش در دفتر هزینه ثبت نشوند، صفحه به‌جای عدد
  ساختگی، استعلام تلفنی را نشان می‌دهد.
- کدِ QR چاپ‌پذیر در `public/images/menu-qr.svg` به مسیر بالا اشاره می‌کند؛ با
  `npm run menu:qr` دوباره ساخته می‌شود. در فوتر صفحهٔ اصلی لینک دریافت QR هست.
- منوی صفحهٔ اصلی و `/menu` از `src/data/pizzas.ts` به‌عنوان یک منبع مشترک استفاده می‌کنند.
- عکس‌های غذا تصویرسازیِ مفهومیِ تولیدشده‌اند، نه عکسِ واقعیِ محصولات؛
  برای انتشار نهایی می‌توان آن‌ها را با عکس‌های واقعیِ آشپزخانه جایگزین کرد.


```bash
npm install
npm run dev        # http://localhost:5173
npm run build      # خروجی در dist/
npm run preview    # پیش‌نمایشِ نسخهٔ ساخته‌شده
npm run typecheck  # بررسی تایپ‌ها
npm run fonts      # بازسازی public/fonts/fonts.css پس از افزودن فونت
```

## ۱. فونت مدام (Modam)

فونتِ فعالِ **تمام سایت و اپلیکیشن `/cost`، برای متن‌های فارسی و لاتین، تیترها و رابط**،
MODAM است. فایل‌های WOFF2 در `public/fonts/` قرار دارند: ۸ وزنِ اصلی و ۸ وزنِ
فشرده. وزنِ عادی در کل رابط استفاده می‌شود؛ زیرخانوادهٔ فشرده جداگانه ثبت شده است.

`index.html` فونت‌ها را برای هر دو مسیر بارگذاری می‌کند و `src/styles/global.css`
تمام خانواده‌های تایپوگرافی را روی MODAM قرار می‌دهد. فایل CSS از روی فونت‌های پوشه
تولید می‌شود:

```bash
npm run fonts
```

این دستور `public/fonts/fonts.css` را بازسازی می‌کند؛ پس از افزودن یا جایگزین‌کردن
فایل‌ها، همین دستور و سپس `npm run build` را اجرا کنید. فایل‌های MODAM تجاری هستند؛
مجوز فونت باید استفاده و میزبانیِ وب را پوشش دهد، به‌خصوص اگر مخزن GitHub عمومی است.

| خانواده | کاربرد |
|---|---|
| **MODAM** | فونت اصلیِ فارسی و لاتین در کل سایت و `/cost` |
| **MODAM Condensed** | زیرخانوادهٔ فشرده؛ برای استفادهٔ صریح در طراحی |
| Vazirmatn، Outfit، Bodoni Moda | فایل‌های محلیِ جایگزین/قدیمی؛ خانوادهٔ فعال رابط نیستند |

فونت‌ها از همان دامنه بارگیری می‌شوند؛ CDN خارجی لازم نیست.

## ۲. داده‌های مبنا

داده‌های اولیه مستقیماً از فایل `menu cost-1400-04-16.pdf` استخراج و در
`src/data/seed.ts` نشانده شده‌اند:

| موجودی | تعداد |
|---|---|
| مواد اولیه (با تاریخچهٔ قیمت) | ۱۱۳ |
| آیتم‌های منو | ۲۶ |
| دستورهای نیمه‌ساخته (سس‌ها، خمیرها …) | ۱۷ |
| آیتم‌های سربار | ۹ |
| ردیف‌های دستور پخت | ۳۲۸ |

## ۳. فرمول محاسبه (مطابق فایل منبع)

```
بهای مواد       = Σ (مقدار × قیمتِ جاریِ ماده)
جمع × ضریب      = بهای مواد × ضریبِ دستور (پیش‌فرض ۳)
سربارِ پایه     = (جمع × ضریب) / تعداد پرسِ ماهانه × Σ سربارِ انتخابیِ آیتم
ضریبِ اضافی     = سربارِ پایه × ضریبِ اضافیِ سربار
بهای ناخالص     = (جمع × ضریب) + سربارِ پایه + ضریبِ اضافی + هزینهٔ ظرف
بهای تمام‌شده   = بهای ناخالص (برای هر آیتم)  ·  بهای هر واحد (برای نیمه‌ساخته‌ها)
سود             = قیمت منو − بهای تمام‌شده
حاشیهٔ سود      = سود ÷ قیمت منو
فودکاست         = بهای مواد ÷ قیمت منو
قیمت پیشنهادی   = بهای تمام‌شده ÷ (۱ − حاشیهٔ هدف)
```

دستورهای نیمه‌ساخته به‌صورت بازگشتی (با تشخیصِ دور) قیمت‌گذاری می‌شوند؛
اگر سرباری را روی آیتمی انتخاب نکنید، هزینهٔ آن صفر منظور می‌شود.

## ۴. بخش‌ها

- **نگاه کلان** — KPIهای زنده، نمودار ترکیب هزینه، آیتم‌های زیرِ حاشیهٔ هدف، شاخص سلامتِ اقتصادی منو
- **مواد اولیه** — جست‌وجو، مرتب‌سازی، افزودن/ویرایش/حذف، ثبت قیمت با **تقویم شمسی**
  (تاریخِ خالی ⇒ امروز به‌طور خودکار)، نمودار روند قیمت، تشخیص تغییرِ قیمت
- **آیتم‌ها و دستور پخت** — تعریف آیتم + موادِ تشکیل‌دهنده با مقدار، ضریبِ هر آیتم،
  انتخاب سربارها از لیست، هزینهٔ ظرف، گروه‌بندی (منو / نیمه‌ساخته)
- **هزینه‌های سربار** — ۹ آیتم مبنا + افزودن آیتم جدید، خلاصهٔ اثرِ هر سربار روی منو
- **قیمت‌گذاری منو** — جدولِ زنده (فیلتر، جست‌وجو، مرتب‌سازی، فقط زیرِ هدف)، افزایشِ
  گروهی (+۵٪)، گردکردنِ هوشمند، خروجی اکسل، اِعمال قیمت پیشنهادی، و تبِ **کارت‌های منو**
- **تنظیمات** — نام رستوران/سرآشپز، حاشیهٔ هدف، تعداد پرسِ ماهانه، **ضریبِ اضافیِ سربار**،
  واحد پول، پشتیبان/بازیابی JSON، خروجی CSV، و کارتِ **سلامت داده‌ها** برای رفع تضادهای
  قیمتِ به‌جامانده از فایل منبع

## ۵. طراحی و ریسپانسیو

- تم: سبزِ تازه، کتان و گرافیت — هماهنگ با نگاهِ ورزشکار/سلامت‌محورِ سرآشپز
- **لوگو**: حرف F که خودش یک شاخهٔ سبز است (ساقه + دو برگ)، با هالهٔ نوری،
  تابشِ عبوری و تکانِ ملایمِ برگ‌ها — فایل‌های مستقل در `public/brand/`
- **واکنش‌گرایی**: از ۳۲۰px تا ۱۹۲۰px
  - `< 900px`: ناوبریِ پایین + منوی کشویی، جدول‌ها تبدیل به **کارت‌های ردیف**،
    مودال‌ها به‌صورت شیت از پایین، فهرستِ آیتم‌ها به‌صورت لیست → جزئیات
  - `900–1199px`: نوارِ کناریِ باریک (فقط آیکون)
  - `≥ 1200px`: نمای کامل با نوارِ کناری
- **افکت‌ها**: نورِ دنبال‌کنندهٔ نشانگر روی کارت‌ها، هاله‌های رنگیِ متحرک،
  درخشش روی دکمه، موجِ کلیک، نمایشِ تدریجی هنگام پیمایش، شمارندهٔ اعداد،
  و **هر آیکون یک انیمیشنِ مخصوصِ خودش** (ضربانِ قلب، تکانِ برگ، چرخشِ بروزرسانی،
  باز شدنِ درِ سطل زباله، پریدنِ سکه، جرقه، کشیده شدنِ تیک …)
- همهٔ انیمیشن‌ها به `prefers-reduced-motion` احترام می‌گذارند و فونت‌ها محلی‌اند

## ۶. انتشار روی گیت‌هاب

> مخزن از پیش `git init` شده و همه چیز کامیت شده است؛ فقط مخزن را در
> github.com بسازید و این دستورها را بزنید (مخزن را **بدون** README و LICENSE
> بسازید چون هر دو در پروژه هستند):

```bash
cd farya-app
git remote add origin https://github.com/USERNAME/farya-chef-console.git
git branch -M main
git push -u origin main
```

اگر از SSH استفاده می‌کنید:

```bash
git remote add origin git@github.com:USERNAME/farya-chef-console.git
git push -u origin main
```

هر push/pull request روی `main`، workflowِ `.github/workflows/ci.yml` را اجرا
می‌کند: نصب، `typecheck`، `build`، و بارگذاریِ خروجیِ `dist`.

### چه چیزهایی آپلود می‌شوند؟

همه چیزِ لازم از پیش در مخزن است (۶۶ فایل، حدود ۳ مگابایت). این‌ها **آپلود
نمی‌شوند** (در `.gitignore` هستند) و نباید هم بشوند:

| مسیر | چرا |
|---|---|
| `node_modules/` | ورسل خودش نصب می‌کند |
| `dist/` | خروجیِ build است، ورسل خودش می‌سازد |
| `.env.local` | **کلیدهای شما — هرگز آپلود نشود** |
| `.vercel/` | پوشه‌ی محلیِ ورسل |

### ⚠️ درباره‌ی فونتِ مدام

فونت‌های **مدام (MODAM) تجاری هستند و حقِ نشر دارند**. آن‌ها را در مخزنِ
**عمومی** آپلود نکنید. دو راه دارید:

1. مخزن را **Private** کنید و فایل‌ها را در `public/fonts/` بگذارید، یا
2. مخزن عمومی باشد و فایل‌های مدام را فقط روی ورسل بریزید
   (با آپلود در Settings یا از طریق Git LFS با دسترسیِ محدود).

بدونِ مدام هم برنامه می‌کند — به‌طور خودکار از Vazirmatn و Bodoni Moda استفاده
می‌شود و فقط ظاهرِ تیترها کمی فرق می‌کند.

## ۷. دپلوی روی ورسل

**روش ۱ — از طریق گیت‌هاب (توصیه‌شده):**

1. به [vercel.com](https://vercel.com) وارد شوید و *Add New → Project* را بزنید.
2. مخزنِ `farya-chef-console` را Import کنید.
3. **پیش از زدنِ Deploy، متغیرهای محیطی را وارد کنید** (پایین را ببینید).
4. تنظیمات به‌طور خودکار از `vercel.json` خوانده می‌شود:
   - Framework: `Vite`
   - Build Command: `npm run build`
   - Output Directory: `dist`
   - Install Command: `npm ci`
5. *Deploy* را بزنید. از این به بعد هر push روی `main` خودکار دپلوی می‌شود.

### 🔴 مهم‌ترین قدم: متغیرهای محیطی

اگر می‌خواهید داده‌ها واقعاً در پایگاه‌داده بمانند، این دو را در
**Settings → Environment Variables** وارد کنید (برای Production و Preview):

| Name | Value |
|---|---|
| `VITE_SUPABASE_URL` | نشانیِ پروژه، مثل `https://abcdefgh.supabase.co` |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | کلیدِ عمومیِ publishable پروژه (هرگز secret key را اینجا نگذارید) |

بعد از افزودن، حتماً **Redeploy** کنید — متغیرهای `VITE_` هنگامِ build در
کد جاسازی می‌شوند و روی دیپلوی‌های قبلی اثر نمی‌گذارند.

> اگر این دو را وارد نکنید، برنامه باز هم بالا می‌آید و کار می‌کند، اما داده‌ها
> فقط در مرورگرِ همان دستگاه می‌مانند (نشانگر بالای کارتِ سرآشپز می‌گوید
> «ذخیره در مرورگر»).

**روش ۲ — با CLI:**

```bash
npm i -g vercel
vercel pull          # پیوند دادنِ پروژه
vercel env add VITE_SUPABASE_URL
vercel env add VITE_SUPABASE_PUBLISHABLE_KEY
vercel --prod        # دپلویِ نهایی
```

فایل `vercel.json` در مخزن تنظیماتِ لازم را دارد: بازنویسیِ SPA، کشِ یک‌ساله
برای فونت‌ها و خروجیِ build، و هدرهای امنیتی.

برای دامنهٔ اصلی، در **Vercel → Project → Settings → Domains**، دامنهٔ
`farya-pitza.ir` را به همان پروژه اضافه کنید (در صورتِ استفاده، `www` را هم).
رکوردهای DNS را دقیقاً از صفحهٔ Vercel کپی کنید و در Cloudflare با مقادیرِ
فعلی تطبیق دهید؛ چون دامنه هم‌اکنون به Cloudflare متصل است، DNS را بی‌دلیل
تغییر ندهید. دامنهٔ canonical سایت بدون `www` است.

## ۸. پایگاه‌دادهٔ سوپابیس (ذخیره‌سازی دائمی)

برنامه به‌صورت پیش‌فرض روی مرورگر کار می‌کند. برای اتصال داده‌های برنامه به پایگاه‌داده، اسکریپت‌های SQL در پوشهٔ `supabase/`
قرار دارند. فایلِ `07_public_menu.sql` یک migration افزایشی و فقط‌خواندنی برای منوی آنلاین است.

### گام ۱ — ساخت پروژه

1. پروژهٔ Supabase خود را باز کنید (در این استقرار: **FARYA**).
2. از **Project Settings → API Keys** این دو مقدار را بردارید:
   - Project URL
   - کلیدِ `Publishable` (`sb_publishable_…`)

### گام ۲ — اجرای اسکریپت‌ها

در **SQL Editor** پروژه، فایل‌ها را **به همین ترتیب** اجرا کنید:

| فایل | کاری که انجام می‌دهد |
|---|---|
| `supabase/01_schema.sql` | جدول‌ها، اندیس‌ها، تریگرها و توابعِ تقویمِ شمسی |
| `supabase/02_functions.sql` | موتورِ محاسبهٔ بهای تمام‌شده و رویه‌های عملیاتی |
| `supabase/03_rls.sql` | RLS محدود به کاربرانِ واردشده، دسترسی‌ها و Realtime |
| `supabase/04_seed.sql` | داده‌های پایهٔ قدیمی برای یک پروژهٔ تازه |
| `supabase/05_verify.sql` | آزمون‌های سازگاری و امنیت |
| `supabase/07_public_menu.sql` | feed عمومیِ فقط‌خواندنی برای ۷ کدِ FARYA؛ تنها تابع قیمت فروش را برمی‌گرداند |

> **هشدارِ مهم:** فایل‌های ۰۱ تا ۰۵ و `00_all-in-one.sql` فقط برای یک پروژهٔ خالی‌اند؛
> روی پروژهٔ تولیدیِ پُرداده اجرا نکنید. `save_state()` جدول‌های رابطه‌ای را بازسازی می‌کند.
> برای پروژهٔ موجود فقط migration افزایشیِ `07_public_menu.sql` به‌کار می‌رود؛ این migration
> با نام `add_public_menu_feed` در پروژهٔ فعلی اجرا شده است.
>
> ترتیب bootstrap مهم است: ۰۱ باید پیش از ۰۲ اجرا شود (ستونِ `gdate` به تابعِ تبدیل وابسته است).
> سیاست RLS همچنان فقط نوشتنِ کاربرانِ `authenticated` را می‌پذیرد؛ نقشِ `anon` فقط اجازهٔ
> اجرای RPC محدودِ قیمت منوی عمومی را دارد و دسترسیِ نوشتن ندارد.

> **همهٔ فایل‌ها SQLِ خالص هستند** و هیچ دستورِ خطِ‌فرمانی (مانند `\set`) ندارند،
> بنابراین مستقیماً در SQL Editorِ سوپابیس اجرا می‌شوند.
> (اگر خطای `syntax error at or near "\"` دیدید، یعنی فایل با ابزارِ `psql`
> ساخته یا دستکاری شده است — از فایلِ اصلیِ مخزن استفاده کنید.)

### بازسازی و آزمایشِ اسکریپت‌ها

فایلِ یکپارچهٔ نصبِ تازه از روی فایل‌های bootstrap و migration ساخته می‌شود؛ بعد از هر تغییر آن را
دوباره بسازید. این فایل را روی پروژهٔ تولیدی اجرا نکنید:

```bash
npm run db:sql      # ساختِ supabase/00_all-in-one.sql
```

اگر PostgreSQL روی دستگاه دارید، می‌توانید اسکریپت‌ها را دقیقاً به شیوهٔ
SQL Editorِ سوپابیس (یک پرس‌وجوی ساده، بدونِ هیچ دستورِ خطِ‌فرمانی) آزمایش کنید:

```bash
npm run db:test                       # اجرای فایلِ یکپارچه روی یک پایگاهِ تازه
npm run db:test -- supabase/01_schema.sql supabase/02_functions.sql \
                   supabase/03_rls.sql supabase/04_seed.sql supabase/05_verify.sql
DATABASE_URL=postgres://... npm run db:test    # روی یک پایگاهِ دلخواه
```

### گام ۳ — احراز هویت و امنیت

این نسخه فقط به کاربرِ واردشده اجازه می‌دهد به داده‌ها دسترسی پیدا کند؛ ثبت‌نامِ
عمومی در پروژهٔ FARYA خاموش است. در **Authentication → Users** حسابِ سرآشپز را
به‌صورتِ دستی بسازید و آن را تأیید کنید. برنامه صفحهٔ ورود و بازیابیِ گذرواژه دارد.
برای ورود فقط ایمیل و گذرواژهٔ همان کاربر به کار می‌رود.

> کلیدِ `Publishable` برای مرورگر است و در build دیده می‌شود؛ این رفتار طبیعی است.
> **کلیدِ `Secret` را هرگز در Vite، مرورگر، GitHub یا متغیرهای `VITE_*` نگذارید.**
> کلیدِ Secretی که در گفت‌وگو افشا شده را از **Project Settings → API Keys**
> بچرخانید/لغو کنید؛ برای اتصالِ سمتِ مرورگر به آن نیازی نیست.

### گام ۴ — اتصالِ برنامه

فایل `.env.example` را کپی کرده و نامش را `.env.local` بگذارید، سپس پر کنید:

```bash
cp .env.example .env.local
# سپس مقادیر را ویرایش کنید:
VITE_SUPABASE_URL=https://xxxxxxxxxxxx.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=sb_publishable_...
```

و سرور را دوباره راه‌اندازی کنید:

```bash
npm run dev
```

از این لحظه، ابتدا صفحهٔ ورود می‌آید؛ پس از ورودِ حسابِ سرآشپز، نشانگرِ بالای
کارت وضعیت را نشان می‌دهد (**ذخیره در پایگاه‌داده** = متصل) و با کلیک روی آن
همگام‌سازیِ دستی انجام می‌شود.

### روی ورسل

همین دو متغیر را در **Vercel → Project → Settings → Environment Variables**
(برای Production و Preview) اضافه کنید و دوباره دیپلوی کنید. نشانیِ دامنهٔ نهایی
را نیز در Supabase → Authentication → URL Configuration در `Site URL` و
`Redirect URLs` مجاز کنید.

### نکته‌های فنیِ مهم

- **موتورِ محاسبه در پایگاه‌داده هم پیاده شده است** (`cost_all()`, `cost_item()`)
  و خروجی‌اش با موتورِ تایپ‌اسکریپتِ برنامه (`src/lib/calc.ts`) روی تمامِ
  ۴۳ آیتم و ۵۱۷ مقدار **کاملاً یکسان** است (تستِ تطبیقی انجام شده).
- **تقویمِ شمسی در SQL** با الگوریتمِ JDN نوشته شده و با موتورِ برنامه روی
  **۱۳٬۱۴۹ تاریخ** در هر دو جهت تطبیق داده شده (۰ اختلاف).
- توابع با `plpgsql` نوشته شده‌اند تا PostgreSQL آن‌ها را درونِ پرس‌وجوها
  «inlined» نکند؛ در غیر این صورت زمانِ برنامه‌ریزی به‌شدت بالا می‌رود
  (۱۴ دقیقه در برابرِ ۰٫۳ ثانیه).
- **همگام‌سازی اتمیک است**: رویهٔ `save_state()` کلِ وضعیت را در یک تراکنش
  به جدول‌های رابطه‌ای تجزیه می‌کند — یا همه چیز ثبت می‌شود یا هیچ چیز.
- **هیچ داده‌ای از دست نمی‌رود**: هر ذخیره یک نسخه در `app_state_history`
  می‌گذارد و هر تغییر در `audit_log` ثبت می‌شود.
- **اتصالِ اینترنت قطع شود** هم برنامه کار می‌کند؛ تغییرات در مرورگر می‌مانند و
  با وصل شدنِ دوباره خودکار همگام می‌شوند.
- اگر دو دستگاه همزمان ویرایش کنند، وضعیت‌ها **ادغام (merge)** می‌شوند،
  نه اینکه یکی دیگری را از بین ببرد.
